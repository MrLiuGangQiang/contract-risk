# 09 非功能性需求与运维设计

> 非功能性需求（NFR）与运维保障是企业级评审必查项。本文档给出本阶段量化目标与运维策略；实际数值在部署环境确定后与运维/安全团队对齐确认。

## 1. 非功能性需求（NFR）

| 类别 | 指标 | 目标值 | 说明 |
| --- | --- | --- | --- |
| 性能 | 常规 API 响应时间 | P95 ≤ 300ms | 不含外部依赖（钉钉）的本地处理 |
| 性能 | 登录接口响应时间 | P95 ≤ 500ms | 本地账密登录；钉钉登录另计外部调用 |
| 性能 | 并发能力 | 初始支持 ≥ 100 并发 | 无状态水平扩展，可增加 worker 扩容 |
| 可用性 | 服务可用性 | ≥ 99.9%（月停机 ≤ 43min） | 生产环境目标，需多副本部署 |
| 数据 | RPO / RTO | RPO ≤ 24h（每日全量备份），RTO ≤ 4h | 启用 WAL 归档可进一步提升 RPO |
| 安全 | 漏洞管理 | 关键依赖无已知高危漏洞 | CI 依赖扫描 |
| 可维护 | 部署 | 发布可回滚、迁移可逆 | 见《07-工程规范与代码规范》 |

> 注：上述 SLO 数值为「建议基线」，最终以企业实际 SLA 要求为准，部署前评审确认。

## 2. 性能设计要点

- 数据库：常用查询走索引（见《03-数据模型设计》第 7 节）；列表查询强制分页；慢查询阈值 200ms 记录并告警。
- Redis：配置缓存、令牌、限流均走 Redis；单次请求 Redis 往返 ≤ 2 次（登录等特殊场景除外）。
- 外部依赖（钉钉）：一律超时控制（连接 5s / 读取 10s），失败快速失败并转统一错误码，禁止无限重试阻塞。
- 连接池：DB 连接池上限按「worker 数 × 每 worker 10~20」配置（默认 `DB_POOL_SIZE=10` / `DB_MAX_OVERFLOW=20`，含 `DB_POOL_TIMEOUT`/`DB_POOL_RECYCLE`/`DB_POOL_PRE_PING`）；Redis 连接池复用（`REDIS_MAX_CONNECTIONS=50`，可调）。

## 3. 可观测性

### 3.1 日志

JSON 结构化日志 + request_id 全链路（见《07-工程规范与代码规范》第 7 节）。

### 3.2 指标（Metrics）

- 暴露 `/metrics`（Prometheus 格式），指标包括：
  - HTTP：请求量、延迟分布（P50/P95/P99）、错误率（按状态码/路径）。
  - 业务：登录成功/失败数、钉钉回调失败数、令牌刷新失败数。
  - 资源：DB 连接数、Redis 延迟与错误、worker 进程数。
- 告警规则（建议）：5xx 率 > 1%（5 分钟）、P95 延迟 > 1s（5 分钟）、DB 连接池耗尽、Redis 不可用、登录失败率突增。

### 3.3 集中日志

生产环境日志集中收集（Loki/ELK，Phase 1 收尾与运维对齐），支持按 request_id 检索。

## 4. 备份与恢复

| 项 | 策略 |
| --- | --- |
| PostgreSQL | 每日全量备份（pg_dump）+ WAL 归档支持 PITR；备份加密、异地/对象存储保存 |
| 恢复演练 | 每季度至少一次恢复演练，验证 RTO/RPO |
| Redis | 数据可重建（缓存/令牌可失效重登），不作为唯一数据源；生产按需开启 AOF |
| 配置 | 密钥与 .env 由部署平台保管，不依赖开发者本机 |

## 5. 容量规划（初始）

- 用户规模预估：≤ 1,000 人（钉钉企业规模内）。
- 合同量：Phase 3 上线前重新评估存储与计算资源。
- 日志表按月归档，避免无界增长。

## 6. 发布与运维流程

- 变更流程：开发 → CI（lint/type/test/scan）→ 测试环境验证 → 评审 → 生产发布。
- 发布窗口：非工作时间；数据库迁移先行、应用代码后发；失败立即回滚。
- 环境隔离：dev / test / prod 三套环境，配置互不串用。

## 7. 数据留存与合规

- 登录日志、操作日志：保留 ≥ 180 天（以企业合规要求为准），按月归档。
- 用户隐私：仅采集业务必需信息；导出/删除按企业合规流程执行。

## 8. 容器化与镜像规范（Phase 1 交付）

- 镜像仓库：`registry.cn-hangzhou.aliyuncs.com/liugangqiang/contract-risk`（阿里云 ACR）。
- 镜像形态：**单一一体化镜像**（根目录 `Dockerfile`，多阶段构建）：
  - 阶段一（node:22-alpine）构建 Vue3 前端静态资源；
  - 阶段二（python:3.12-slim）安装 Nginx 与后端锁定依赖，托管前端静态资源并将 `/api` 反向代理到同容器内 `127.0.0.1:8000` 的 Uvicorn；
  - 启动入口 `entrypoint.sh`：先启动 Uvicorn（可配 `UVICORN_WORKERS`），后端就绪后以前台方式启动 Nginx。
- 数据库迁移：独立 `migrate` 一次性服务（同一镜像）先执行 `alembic upgrade head`，应用服务 `depends_on` 其成功后启动，避免多副本竞争迁移。
- 敏感配置：镜像内不含 `.env`/密钥；构建上下文 `.dockerignore` 排除 `.env`、`node_modules`、`dist`、`.venv`、`docs` 等；运行期配置全部通过 compose 环境变量注入。
- 健康检查：应用容器经 Nginx 探测 `GET /api/v1/health`；compose 对 PostgreSQL/Redis 配置健康检查后启动依赖服务。
- 标签规范：`<版本号>`（如 `v0.1.0`）用于生产；`latest` 仅限本地调试；`sha-<7>` 标识具体提交。
- CI/CD：GitHub Actions（`.github/workflows/build-push-acr.yml`）在 push main / tag `v*` / 手动触发时自动构建并推送镜像；ACR 登录凭证通过 GitHub Secrets（`ACR_USERNAME` / `ACR_PASSWORD`）注入，不入库。
- 构建与推送命令与部署步骤：见 `docs/ops/部署指南.md`。
